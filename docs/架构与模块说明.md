# 架构与模块说明

## 总体结构

应用是单一 Rust 二进制 crate。GPUI 负责窗口和界面；`AppState` 保存导航、操作状态和持久化设置；Windows 系统能力由应用内的模块封装。

```text
src/main.rs
  ├── AppState（src/app.rs）
  ├── MainWindow（src/ui/main_window.rs）
  ├── 视觉组件（src/ui/components.rs）
  └── 后端任务（src/backend.rs 与系统模块）
```

## 启动和生命周期

1. Windows 入口检查提权状态；未提权时通过 Shell 请求管理员权限，并结束当前实例等待提升后的新实例。
2. 使用本地命名互斥量保持单实例。再次启动时尝试聚焦已有主窗口后退出。
3. 初始化 `config/logs/rust-win-tool.log` 追加日志。
4. 创建 GPUI 应用、窗口和 `AppState`，加载语言、主题、管理服务列表及自定义脚本。
5. 刷新服务状态并安装 Windows 通知区域图标。

提权取消时不继续以普通权限运行。UAC、单实例和托盘属于 Windows 特定行为。

## 状态和界面

- `AppState` 位于 `src/app.rs`，持有当前页面、服务数据、工具选择、清理状态、对话框、脚本和设置。
- `View` 表示主导航页面：`Service`、`Tools`、`Cleanup`、`Scripts`、`Settings`。
- `MainWindow` 位于 `src/ui/main_window.rs`，读取状态并构造页面，处理 GPUI 事件。
- `components.rs` 提供卡片、按钮、状态徽标和窗口控件等视觉基础组件。
- `input.rs` 管理局部文本输入行为，不注册全局快捷键。
- `i18n.rs` 定义中英文字串，页面通过当前 `AppState` 的翻译表取值。
- `theme.rs` 保存与 UI 框架无关的主题颜色，再由 GPUI 层转换。

## 后台任务与错误

系统查询、文件操作和注册表操作可能阻塞，因此 UI 事件通常将工作提交到 GPUI `background_spawn`，完成后回到主线程更新 `AppState` 并通知界面刷新。

`src/backend.rs` 汇总 UI 使用的后端入口，并把服务、命令、注册表和解析错误转换为 `BackendError`。服务错误的显示文本保留用于 UI 错误映射的关键词。后台操作仍受 Windows 权限、目标程序状态和系统 API 结果影响。

## 源文件索引

|---|---|
| `main.rs` | GPUI 启动、Windows 提权、单实例和托盘初始化 |

## 数据流示例：服务启动

```text
用户点击启动
    ↓
MainWindow 创建后台任务
    ↓
backend::start_service
    ↓
service::start_service（Windows Service Control Manager API）
    ↓
后台任务返回结果
    ↓
AppState 更新状态/错误消息
    ↓
GPUI 通知并重绘服务行
```

其他慢操作采用相同模式。不要在 GPUI 事件处理器内直接运行耗时的系统 API、PowerShell 子进程或大量文件遍历。

## Windows API 与依赖

- `gpui`：桌面窗口与渲染。
- `serde`、`serde_json`：配置、服务列表和自定义脚本数据。
- `thiserror`：错误类型。
- `winreg`：Windows 注册表。
- `windows-sys`：Service Control Manager、进程、网络、文件系统、Shell、窗口和系统信息 API。
- `raw-window-handle`：取得原生窗口句柄以安装托盘图标。
- `winresource`：Windows 图标及版本资源构建。

服务管理实现已内联至 `src/service.rs`，新增服务能力时直接扩展该模块和其调用层，不需要维护独立服务 crate。
